# AGENTS.md

Guidance for coding agents working on the **forgebatch** Textual TUI. Read this
before editing; it explains the architecture, invariants, and how to verify
changes.

## What this is

An interactive TUI (`python3 forgebatch.py`) that generates SLURM/PBS job
directories for HPC scheduler experiments. It is a self-contained reimplementation
of the legacy `submit_gui.py` / `submit_tui.py` tools (which live in the
parent repo and are intentionally left untouched — do not import from them).

## Architecture / module map

| File | Responsibility | Imports |
|------|----------------|---------|
| `forgebatch.py` | Launcher: prepends its dir to `sys.path`, calls `app.main()` | `app` |
| `config.py` | Constants (`name`, `scheduler`, `use_slurm`, `home_dir`, `config_file`) + `default_settings`/`read_config`/`write_config`/`set_config_file`/`next_job_id` | stdlib only |
| `builder.py` | Pure job-generation logic: `is_scalar`, `job_chains`, `dependency_flags`, `job_header`, `_read_resolved`, `_data_entry`/`collect_dims`, `validate_data`, `sweep_value_spans`, `substitute_placeholders`, `unknown_tokens`, `build_jobs` (emits `files`/`dirs`/`file_links` per variant) | `config`, `diffing`, `yaml` (PyYAML) |
| `diffing.py` | Pure edit persistence: `compute_patch`, `apply_patch`, `is_patch`, `resolve_edit` (git-style unified diffs) | stdlib only |
| `runner.py` | Pure submission helpers: `run_submission` (submit jobs honouring the parallelism limit, injecting dependencies at submit time) and `parse_running_output` (squeue/qstat text → structured records `{job_id, name, user, state, elapsed_sec, limit_sec, queue}`) + pure helpers `parse_duration`/`state_category`/`progress_cells`/`cancel_cmd`/`detail_cmd` | stdlib, `builder` |
| `widgets.py` | `FilePane` composite widget (browse + path input + remove + debounced editable content, error label, symlink/copy toggle, optional side-by-side diff view) | `textual`, `builder`, `diffing` |
| `screens.py` | Modal screens: `PanelModal` base + `FileBrowserScreen`, `PromptScreen`, `PresetsScreen`, `HelpScreen`, `SubmitLogScreen`, `JobDetailsScreen`, `ConfirmScreen`, `format_submit_log` | `config` |
| `app.py` | `ForgeBatchApp` (CSS, compose, custom tab bar, actions, Preview pane, Jobs queue pane) + `main()` | `builder`, `config`, `screens`, `widgets` |

There are **no circular imports**; the dependency direction is
`app -> screens/widgets -> config` and `app -> builder -> config`. Keep it
that way. `builder.py` must stay **Textual-free** so it is unit-testable.

## Key invariants (do not break)

1. **Source files are never modified.** Edits and sweep variants only affect
   copies written into generated job directories. `build_jobs` reads source
   files but never writes to them.
1b. **Existing write targets are guarded.** `builder.existing_targets(variants)`
    returns `{"kind", "path"}` entries for every write target that already
    exists on disk (`os.path.lexists`, so a dangling symlink is also flagged):
    the job file, copied files, and directory/file symlinks. A job dir that
    already exists as a *directory* is **not** a conflict (single-job in-place
    writes into the root by design), but one that exists as a *file* is always
    flagged. `app.action_preview` surfaces these in the
    `#preview_conflicts` Static (with a `conflict` class) and disables writing
    until the user presses **Override conflicts**, which sets
    `self._override_conflicts` to allow `app._write` (and `_confirm_submit`) to
    proceed. The override resets after each write.
2. **The job body is one text block.** The Settings tab has a single editable
   **job body** pane (`#job_body_editor`) whose content is appended verbatim to
   the generated `job.slurm`/`job.pbs` file right after the scheduler header.
   It is    stored as the plain string `fields["job_body"]` (no backing file, no
   diff) and filled by **Import job from file** / **Import job from text**
   (`app._apply_import`, via `builder.parse_import`, which strips the
   header-owned directive lines and the email and returns `(email, body)`) or
   typed directly; **Clear** resets it to a commented template
   (`# cd {{JOBDIR}}` / `# echo {{JOBID}}`). The scheduler header
   itself is generated by `builder.job_header` and shown read-only. Included
   *files* are copied into the job dir (or symlinked when their entry has
   `mode: "symlink"`); nothing is embedded from the file list.
2b. **Included items: files and directories, copy or symlink.** `included_files`
    entries are `{"path", "mode"}` with `mode` `"copy"` (default) or
    `"symlink"`; `included_dirs` entries are `{"path", "mode"}` with `mode`
    `"symlink"` (default) or `"copy"`. `builder.build_jobs` emits per variant:
    `files` (copied, editable/swept content), `dirs` (copied or symlinked
    directories, never edited/swept), and `file_links` (symlinked files, never
    read/edited/swept; missing ones warn). The builder is pure — it only
    describes these; `app._write` performs the actual `open`/`copytree`/
    `os.symlink`. Symlinked files are not editable, not swept, and carry no
    `file_edits`. Binary files are detected by `FilePane` (`read_text_or_bytes`)
    and their editor is set read-only (`area.read_only = True`), so they cannot
    be edited. The optional **show diff** checkbox (`#show_diff`) toggles a
    side-by-side `#diff_view` (Static) showing `diffing.compute_patch(source,
    current)` live for copy-mode, non-binary files.
3. **Sweep semantics.** Every included *data* file (`.json`, `.yaml`, `.yml`)
   that parses as a mapping contributes dimensions: a key whose value is an
   array is a    dimension when the on-disk base value at that path is a scalar
   (or the path is absent and the array is all scalars). Scalars include
   **strings**, so text arrays are swept too. Keys may be top-level
   **or nested** (a dotted path such as `data.random_linear_transform`);
  `builder.collect_dims` walks nested mappings and never descends into arrays
  of mappings. A single scalar on a key is available for the sweep — replace
  it with an array to sweep it. Dimensions are scoped to `(file_path,
  key_path_tuple)` and combined via Cartesian product; labels use the dotted
  path. Non-swept keys are preserved. Active sweep arrays are highlighted in
  the file view by `widgets.SweepTextArea` (via `builder.sweep_value_spans`,
  which returns `(line, start_col, end_col)` ranges for top-level or nested
  keys). The **job body** also supports inline sweeps: a `[[...]]` region
  containing a JSON array of scalars (ints/floats/strings/bools) is a
  dimension — `python train.py --lr [[1,2,3]]` generates one job per value,
  replacing the `[[...]]` with the bare value per job (`--lr 1`, `--lr 2`,
  `--lr 3`; strings render unquoted, bools as `true`/`false`). Body sweeps
  join the same Cartesian product as data-file sweeps and are labelled by
  their `[[...]]` text. They are detected by `builder.collect_body_sweeps`
  (`OrderedDict[sweep_text -> values]`), located for highlighting by
  `builder.body_sweep_ranges` (`(line, start_col, end_col, is_valid)`), and
  substituted in `build_jobs` via `builder._render_sweep_value`. The job-body
  editor (`widgets.TokenTextArea`) highlights valid `[[...]]` sweeps in cyan
  and invalid ones (malformed/invalid JSON, non-scalar, unclosed) in red.
  Malformed sweeps also produce a warning (`builder.body_sweep_errors`), added
  to `build_jobs`' warnings list and surfaced live in the global status bar by
  `app._update_token_warning` alongside unknown-token and data-file warnings.
4. **Dependencies.** `builder.py` imports **PyYAML** for YAML sweep support.
   The import is guarded (`builder.HAS_YAML`): if PyYAML is absent,
   `.yaml`/`.yml` files degrade to plain copies (no sweep) instead of
   crashing, and `builder.validate_data` reports "PyYAML not installed".
   `validate_data` (parse validity for data files) is surfaced in the global
   `#status_bar` by `app._update_token_warning`, which merges unknown-token
   and data-file warnings into one message and clears when all are fixed.
   `builder.py`/`diffing.py` remain **Textual-free**.
5. **Email and SLURM mail-type.** `email` (e.g. `user@example.com`) is
   used directly in `#SBATCH --mail-user` / `#PBS -M`. When empty, the mail
   lines (`--mail-type`/`--mail-user`, `-m ae`/`-M`) are omitted from the
   generated header. The SLURM `--mail-type` value is a configurable list
   (`mail_type`, default `["ALL"]`) chosen via the `#mail_type_*` checkboxes
   in the Settings pane (SLURM only); `builder.job_header` joins them with
   commas (`--mail-type=BEGIN,FAIL`), rendering an empty list as `NONE` and a
   missing key as `ALL`. `builder.parse_import` returns
   `(email, mail_types, body)` so an imported job's `--mail-type` round-trips
   into the checkboxes via `app._apply_import`/`app._set_mail_type`. Legacy
   `user` configs are migrated to `email` in `app.apply_settings`.
6. **Body toggle is exclusive.** Exactly one `FilePane` has the `job body`
   radio on; the radio-change handler enforces this. *(Removed in the
   include-script refactor — file rows no longer have a body radio.)*
7. **Config persistence is non-fatal.** `write_config` swallows `OSError`. The
   config file defaults to `$XDG_CONFIG_HOME/forgebatch/config.json`
   (`~/.config/forgebatch/config.json`); it can be overridden per-run with the
   `-c/--config` CLI option (`config.set_config_file`) and by tests for
   hermetic runs.
8. **Parallelism limit.** The `parallelism_limit` setting (Preview pane input,
   persisted/autosaved) limits how many jobs run in parallel on submit.
   `builder.job_chains(n, p)` returns round-robin job-index chains (each chain
   runs in series; chains run in parallel; `[]` when no deps needed, i.e.
    `n<=1` or `p<=0`). Dependencies are **injected at submission time** by
    `runner.run_submission` (job ids only exist after submit; called from
    `app._confirm_submit`): it submits each
    chain in order, captures the returned id (`sbatch --parsable` prints just
    the id; `qsub` prints it on stdout), and passes it to the next job via
    `builder.dependency_flags(scheduler, dep_id)` →
    `--dependency=afterok:<id>` (SLURM) / `-W depend=afterok:<id>` (PBS).
    Each `sbatch`/`qsub` runs with `cwd` set to that variant's own job
    directory (`v["job_path"]`), so every job starts directly in its own
    directory (no `cd` needed in the body); single-job mode submits from the
    root itself.
    Dependencies are never baked into job files at build time.
9. **Submission log.** `app._confirm_submit` records the per-job submission log
    returned by `runner.run_submission`
    (`self._submit_log`), writes it to `submit.log` under the job root, and
   pushes the `SubmitLogScreen` modal **only when at least one job failed**.
   `screens.format_submit_log` renders the log for both the modal and the
   on-disk file, so they stay consistent. The `Log` button in the Preview pane
   reopens the last submission's log.
 10. **Jobs queue pane.** The `Jobs queue` tab (`app._refresh_running`) lists the
    current OS user's active scheduler jobs via `squeue` (SLURM,
    `--format=%i|%u|%j|%T|%M|%l`, adding the time limit) or `qstat -x` (PBS,
    XML — see below), run through `asyncio.create_subprocess_exec`
    (non-blocking). `runner.parse_running_output` returns **structured records**
    (`{job_id, name, user, state, elapsed_sec, limit_sec, queue}`); pure
    helpers `runner.parse_duration`, `runner.state_category`,
    `runner.display_state`, `runner.progress_cells`, `runner.cancel_cmd`,
    `runner.detail_cmd` support the view. For PBS, `parse_running_output`
    delegates to `runner.parse_qstat_xml` (`xml.etree.ElementTree`, stdlib) so
    the full **untruncated** `Job_Id` and `Job_Name` are preserved even though
    the fixed-width `qstat` listing cuts them (a truncated id would break
    `qstat -f`/`qdel`); if the text is not XML it falls back to the
    fixed-column parser. `app._render_running` applies the "my jobs only"
    filter, a substring filter (`#running_filter`), and a sort key
    (`#running_sort` Select), then fills a `ListView` (`#running_list`, one real
    `ListItem` per job, no virtualization) where each row is a single rich
    `Text` line — `JOBID NAME USER STATE ELAPSED QUEUE` — with the **state
    colour-coded** by `state_category` (green/yellow/cyan/magenta/red). Long
    job ids/names are **truncated in display only** (full values stay in the
    record, so Details/Cancel are unaffected), and the list is **capped at
    `MAX_RUNNING_ROWS` (200)** jobs with a "Showing first 200 of N jobs"
    message when there are more, so huge queues render without hanging.
    `runner.parse_qstat_xml` still fills `limit_sec` from the
    PBS `<Resource_List><walltime>` request (elapsed from
    `<resources_used><walltime>`, defaulting to 0 for not-yet-started jobs), so
    the record is complete. `_render_running` is `async` (it awaits
    `list.clear()`/`extend(...)` for correct ordering) and is triggered from
    the filter/sort/my-jobs handlers via `call_later`; `_refresh_running`
    awaits it directly. Selection (via `list_view.index`) drives **Details**
    (`app._capture` runs `scontrol show job` / `qstat -f`, shown in a
    `JobDetailsScreen`) and **Cancel** (a `ConfirmScreen`, then
    `scancel`/`qdel` via `runner.cancel_cmd`). It is refreshed manually via the
    Refresh button / on tab open (no automatic polling). No scheduler →
    "No scheduler found".

## Adding a feature

The bullets below note which code files each change touches; remember to also
update the matching docs — see **"Keeping docs in sync"** above.

- **New scheduler field** (e.g. another SLURM option): update
  `config.default_settings`, the Settings grid in `app.compose`, the
   `fields` list in `app.collect_settings`, and
  `builder.job_header`. For SLURM email-notification types, also add the
  option to `app.MAIL_TYPE_OPTIONS`, the `#mail_type_*` checkboxes, and keep
  `builder.parse_import`'s `(email, mail_types, body)` return in sync.
- **Edit the job body**: the job body lives in the editable `#job_body_editor`
  TextArea and is stored as the plain string `job_body` in settings;
  `collect_settings` stores the editor text verbatim, and `builder.build_jobs`
  appends it after the read-only scheduler header rendered by
  `_refresh_job_header`. **Import job from file/text** fills it via
  `builder.parse_import` → `app._apply_import`. The job body and each file
  pane's `#file_content` editor each have an **auto-wrap** `Checkbox`
  (`#job_body_wrap` handled in `app.on_checkbox_changed`, `#file_wrap` in
  `FilePane.on_checkbox_changed`) that toggles the TextArea's reactive
  `soft_wrap` property (UI preference, not persisted).
- **`{{TOKEN}}` placeholders in the job body**: the editor accepts
  `{{JOBID}}` and `{{JOBDIR}}` tokens, replaced per job at build time by
  `builder.substitute_placeholders` (values: job id and job dir path).
  Unknown tokens are left untouched and surfaced: `builder.build_jobs`
  returns a `warnings` list (unknown `{{TOKEN}}` names from
  `builder.unknown_tokens`), which `action_preview` shows in the status bar.
  The global status bar is the `Label` `#status_bar`, rendered at the bottom
  (the Footer has been removed) so it is visible on every tab; it is set by
  `_set_status`. Unknown tokens are also reported live by
  `_update_token_warning` (triggered via `on_text_area_changed` on the job
  body editor) with a `warn` class, clearing once fixed.
  The editor is a `TokenTextArea` subclass that highlights known tokens in
  yellow and unknown ones in red (typo feedback). Token detection uses an
  identifier-like regex (`builder.TOKEN_RE`, `{{[A-Za-z_][A-Za-z0-9_]*}}`),
  so mixed-case typos like `{{JOBDIssR}}` are also flagged, not just all-caps
  ones. `widgets.TokenTextArea` imports `TOKEN_RE`/`KNOWN_TOKENS` from
  `builder` so highlighting and detection stay in sync. To add a token, add
  its name to `builder.KNOWN_TOKENS`, provide a value in `build_jobs`, and, if
  desired, note it in the editor tooltips.
- **New screen** (modal): add it to `screens.py`, push with
  `self.push_screen(..., callback=...)`.
- **New job-generation behaviour**: add pure functions to `builder.py` and a
  matching test in `tests/test_builder.py`.
- **New file tab**: add a button in the `#file_tabs` bar and a `FilePane` in
  `#pane_files` (see `_rebuild_rows`); each included file gets its own tab,
  named by its basename. The Preview tab is right-aligned via `#tab_spacer`.

## Keeping docs in sync

Three human-authored docs describe forgebatch. Keep them in step with the code
whenever you change behaviour — a feature is not done until its docs are too:

- **`AGENTS.md`** (this file) — invariants + architecture/module map for agents.
- **`help.md`** — the in-app **Help** content (rendered by `HelpScreen` via the
  `Help` button / `--help`).
- **`README.md`** — the repo-level, user-facing overview (workflow, usage,
  features). It largely mirrors `help.md`'s feature sections.

When you change code, update every doc it affects:

- A **user-visible** feature or behaviour (a new tab, button, setting, modal,
  sweep rule, …) → update the matching section in `help.md` **and** the
  corresponding paragraph/step in `README.md`. Because `HelpScreen` renders
  `help.md`, never let the two user-facing docs drift from each other or from
  the code.
- An **architectural** change (a module's responsibility, a new invariant, the
  module map, a new test) → update `AGENTS.md` (its invariants,
  "Architecture / module map", and any "Adding a feature" bullet). Add a new
  invariant when you introduce a guarantee future agents must not break.

The **"Adding a feature"** bullets note which code files each kind of change
touches; carry the same diligence into the docs. As a final step before
declaring work complete, confirm `help.md` and `README.md` still describe any
feature you touched (see also "Testing & verification" below).

## Conventions

- Do not add comments unless they clarify non-obvious logic.
- Reuse Textual idioms already present (`ModalScreen` subclasses, `on_*`
  handlers). There is **no Footer**; the only keyboard shortcuts are **Escape**
  (on the main `App`: quit; on modals: cancel/close), **Enter** (modals:
  confirm), **Ctrl+S** (main app: save — `action_save`), and **Ctrl+X** (global
  quit — `action_quit`, works from any screen/dialog because modals do not bind
  it). Everything else is button-driven. There are no `Save`/`Quit` buttons in
  the action bar (save is Ctrl+S; quit is Escape or Ctrl+X). Note:
  `self.tree` collides with a base property — use a distinct attribute name
  (e.g. `self.dirtree`).
- `Grid` comes from `textual.containers`; `RadioButton.Changed` handler is
  `on_radio_button_changed` with `event.radio_button`; a mounted `TextArea`
  needs `load_text()` (setting `.text` doesn't replace the document); a
  `Tree` node carries content in its `data` (`tree.root.add(label, data=...)`).
- The top bar (`#actions`) and tab bar (`#tab_bar`/`#file_tabs`) use
  `overflow-x: auto` and ellipsis-truncated tab buttons (`max-width`,
  `overflow: hidden`, `text-overflow: ellipsis`), so all tabs stay reachable
  via horizontal scroll on narrow terminals instead of being clipped. Bar
  buttons set `min-width: 0; padding: 0 1` to override Textual's default
  `Button { min-width: 16 }` so the top bar fits an 80-column terminal.

## Testing & verification

Run the unit tests (stdlib `unittest`, no external deps) from the repo root:

    python3 tests/test_builder.py          # or: python3 -m unittest discover -s tests
    python3 tests/test_diffing.py
    python3 tests/test_runner.py
    python3 tests/test_config.py
    python3 tests/test_screens.py
    python3 tests/test_preview.py          # TUI end-to-end (needs Textual)

These cover the Cartesian sweep, job-body-appended-after-header,
source-untouched, edit-applies-to-copy, email-in-header (SLURM & PBS), the
submission/dependency chain and scheduler-output parsing (runner), `next_job_id`
(config), and the diff round-trip / merge / conflict invariants.
`tests/test_preview.py` mounts the app headlessly to confirm typed
`{{JOBID}}`/`{{JOBDIR}}` tokens are substituted in the Preview viewer and that
settings autosave / preset-load / preview node-selection behave correctly; it
also covers the Jobs queue pane (row filter/sort/colour/progress, and the
Details/Cancel actions).

For TUI-level checks, scripts like `/tmp/opencode/pilot*.py` drive Textual
headlessly (they monkey-patch the app). When scripting, call action/handler
methods directly rather than simulating pointer clicks (clicks can route to
the Command Palette in headless runs). Because forgebatch's modules (`config`,
`builder`, `app`, `screens`, `widgets`) are imported as top-level names, the
forgebatch directory must be on `sys.path`: either run the script from the
forgebatch repo root or launch it with `PYTHONPATH` set to the forgebatch dir.

Always run `python3 -m py_compile` over the modules after a refactor.

As a final check after any feature change, confirm `help.md` and `README.md`
still describe it (see **"Keeping docs in sync"**).
